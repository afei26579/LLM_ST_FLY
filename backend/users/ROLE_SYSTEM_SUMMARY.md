# 角色权限系统总结

## 系统架构

### 1. 数据模型关系

#### User 模型
- `user_role`: ForeignKey -> Role (新的角色关系)
- `role_str`: CharField (保留的旧字段，用于兼容)
- 关系：一个用户对应一个角色，一个角色可以有多个用户

#### Role 模型
- `code`: 角色代码 (admin, staff, user)
- `name`: 角色名称 (管理员, 工作人员, 普通用户)
- `description`: 角色描述
- `is_system`: 是否为系统角色
- `created_at/updated_at`: 时间戳

### 2. 与Django默认权限系统的关系

#### 当前实现方式
- **自定义角色系统**: 使用独立的Role模型
- **简化权限管理**: 基于角色的访问控制(RBAC)
- **保留Django权限**: 仍可使用Django的Group和Permission系统

#### 优势
1. **简单直观**: 角色概念比权限更容易理解和管理
2. **业务导向**: 角色直接对应业务职能（管理员、工作人员、普通用户）
3. **易于扩展**: 可以轻松添加新角色和修改角色权限
4. **性能优化**: 减少复杂的权限查询，提高API响应速度
5. **前端友好**: 前端可以直接根据角色显示不同的界面和功能

#### 限制
1. **粒度较粗**: 不如Django原生权限系统精细
2. **权限固化**: 角色权限相对固定，不如动态权限灵活
3. **扩展复杂**: 如需要复杂权限控制，需要额外开发

### 3. API接口

#### 角色管理 (`/api/v1/auth/roles/`)
- `GET`: 获取角色列表（需要认证）
- `POST`: 创建角色（仅管理员）
- `PUT/PATCH`: 更新角色（仅管理员）
- `DELETE`: 删除角色（仅管理员，系统角色不可删除）
- `GET /{id}/users/`: 获取角色下的用户列表

#### 用户管理 (`/api/v1/auth/users/`)
- 支持按角色筛选用户
- 支持角色分配和修改
- 包含角色信息的用户序列化

### 4. 权限控制策略

#### 视图级权限
```python
def get_permissions(self):
    if self.action in ['create', 'update', 'partial_update', 'destroy']:
        # 只有管理员可以修改角色
        permission_classes = [permissions.IsAuthenticated, permissions.IsAdminUser]
    else:
        # 所有认证用户都可以查看角色
        permission_classes = [permissions.IsAuthenticated]
    return [permission() for permission in permission_classes]
```

#### 业务逻辑权限
- 系统角色不能删除
- 有用户的角色不能删除
- 角色代码唯一性验证

### 5. 数据迁移策略

#### 迁移步骤
1. 重命名原role字段为role_str
2. 创建Role模型和初始数据
3. 添加user_role外键字段
4. 数据迁移：根据role_str创建角色关联
5. 保留role_str字段用于兼容

#### 迁移安全性
- 保留原始数据
- 分步骤迁移，可回滚
- 数据一致性检查

## 使用建议

### 1. 适用场景
- 中小型项目的权限管理
- 角色相对固定的业务系统
- 需要快速开发的项目

### 2. 扩展方向
- 可以在Role模型中添加permissions字段关联Django权限
- 可以实现角色继承机制
- 可以添加部门、组织等层级结构

### 3. 最佳实践
- 角色设计要符合业务逻辑
- 定期审查角色权限分配
- 记录权限变更日志
- 提供权限测试工具
